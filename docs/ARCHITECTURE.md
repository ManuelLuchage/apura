# Architecture

## Overview

```
 ┌──────────── user's shell (fish today; zsh/bash/nu later) ───────────────────┐
 │  apura init fish | source                                                    │
 │   ├─ wrapper function `apura` ── start/resume/end ──► APURA_EMIT_ENV=fish    │
 │   │                                  ▲ stdout = fish code (sourced)          │
 │   ├─ fish_preexec  → remembers $PWD                                          │
 │   └─ fish_postexec → `apura _record --session … --exit … -- <cmd>` & disown  │
 └───────────────────────────────────────┬──────────────────────────────────────┘
                                         ▼
 ┌──────────────────────────── apura binary (Go) ──────────────────────────────┐
 │ cli (cobra) ──► store (SQLite)   distill (rules + renderers)                 │
 │      │            ▲                   ▲                                      │
 │      ├─ redact ───┘ (before storing)  │                                      │
 │      ├─ tech/cmdparse (technologies, noise)                                  │
 │      └─ shell.Integration (syntax: env, quoting, scripts, init)              │
 └──────────────────────────────────────────────────────────────────────────────┘
```

## Why a wrapper?

A child process cannot change its parent shell's variables. `apura start` must set
`APURA_SESSION` **in the current shell**, so the `apura` function (defined by `init`) runs the
binary with `APURA_EMIT_ENV=<shell>`. The binary prints shell code on stdout (generated by
`Integration.SetEnv/UnsetEnv`) and the function sources it. Human messages go to stderr.
This is the same pattern direnv and zoxide use.

## Life of a step

1. The user runs a command in a shell with an active session.
2. The post-exec hook calls `_record` in the background (the prompt never waits).
3. `_record` filters (empty lines, leading space = private, `apura` commands), masks secrets,
   infers technologies and inserts the step with `seq = MAX(seq)+1` **in a single INSERT
   statement**, which is safe with several shells writing at once (WAL + busy_timeout).
4. `note` and `mark` act on the last step by default.

## Data model

- `sessions`: unique name, goal, state (`active`/`ended`), result, shell, host, timestamps
- `session_tags`: manual tags
- `steps`: command (secrets already masked), **start** cwd, exit code, duration, `mark`, `seq`
- `step_techs`: technologies inferred per step (indexed for `--tech`)
- `notes`: comments on a session (`step_id NULL`) or on a step

`seq` is stable: deleting steps leaves gaps and new steps continue from the maximum. References
the user has seen (`#7`) never change meaning.

**Effective outcome** (`core.Step.Outcome`): the manual mark wins; without a mark, the exit code
decides. `key` implies success.

## Distillation

`distill.Run` applies an ordered list of `Rule`s. Each rule returns what it keeps and what it
removed, so `--show-dropped` can explain every decision.

1. `unsuccessful`: removes steps whose outcome is not success
2. `noise`: removes read-only/navigation commands (`ls`, `cat`, `cd`…) except `key`
3. `repeat`: removes **consecutive** repeats of the same command in the same directory

Renderers re-create `cd` lines from each step's cwd, so recorded `cd` commands can be treated as
noise. Script syntax (shebang, error guard, quoting, code-fence language) comes from the
`Integration` of the shell the session was recorded in.

## Extension points

| I want to… | Where |
|---|---|
| Support another shell | `internal/shell/<name>/` + import in `internal/shell/all` (see SHELL_INTEGRATION.md) |
| Add a distill rule | a type implementing `distill.Rule` + add it to `Pipeline` |
| Add an output format | a `Render<X>(Doc)` function in `internal/distill` + a case in the `distill` command |
| Recognize more technologies | the `programTech` map in `internal/tech` |
| Mask more secret patterns | `rules` in `internal/redact` (+ a test case) |
| Change the schema | a new migration at the end of `internal/store/migrations.go` |
